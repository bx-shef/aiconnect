# Развернуть и подключить к порталу

> Last reviewed: 2026-11-01

## Как устроен выкат

Схема — как в эталоне `client-bank-alfa-by`: **GHCR + Watchtower за общим nginx-proxy** (TLS —
Let's Encrypt). Адрес приложения — **`https://aiconnect.bx-shef.by`**.

| Шаг | Что происходит |
|---|---|
| PR → `main` | `ci` (линт, тесты, типы, сборка) + `docker-build` (образ собирается, в реестр не идёт) |
| push в `main` | только `deploy`: образ `ghcr.io/bx-shef/aiconnect` с тегами `latest` и `sha-<коммит>` |
| сервер | Watchtower раз в ~5 минут видит новый `latest` и пересоздаёт контейнер; nginx-proxy выставляет его наружу по `VIRTUAL_HOST` и выпускает сертификат |

- Проверки (`ci`) идут на PR и на push в `main` не повторяются; `deploy` на `main` только публикует образ (bx-shef/toolsai#312).
- В GHCR пушит встроенный `GITHUB_TOKEN` (`packages: write`), отдельный секрет не нужен.
- Образ один на любой сервер: адрес и секреты он читает из окружения при запуске. Единственный
  build-arg — коммит сборки: его показывает `GET /api/health` (`commit`) и `make doctor`.
- Мерж, который меняет только документацию, тесты, смок, `Makefile` или compose-файлы, образ не
  пересобирает (`paths-ignore` в CI) — прод зря не перезапускается.
- Выкатить заново без коммита — Actions → CI → Run workflow на `main` или `make prod-redeploy` на
  сервере.

## 1. Сервер

### Один раз на хост

nginx-proxy, acme-companion и Watchtower — общие для всего сервера. Если на нём уже крутится
client-bank или currency-converter, они стоят. Проверка:

```bash
docker network ls | grep proxy-net
docker ps --format '{{.Names}}\t{{.Image}}' | grep -E 'nginx-proxy|acme-companion|watchtower'
```

Чего-то нет — поставить по разделу «Если nginx-proxy / Watchtower ещё не стоят» в
[`client-bank-alfa-by/docs/DEPLOY.md`](https://github.com/bx-shef/client-bank-alfa-by/blob/main/docs/DEPLOY.md):
сеть `proxy-net`, прокси из `currency-converter/docker-compose.nginxproxy.yml`, Watchtower с
`--label-enable`. **Второй Watchtower не поднимать**: он конфликтует по имени контейнера и
перезапускает всё дважды.

**Пакет GHCR — публичный**: как сделать — `docs/REPO_SETUP_CHECKLIST.md` §4. Тогда серверу и
Watchtower не нужен `docker login`. Оставляете приватным — на сервере `docker login ghcr.io` с
токеном `read:packages` и креды для Watchtower, как в эталоне («Если репозиторий приватный»).

**Таймаут прокси.** nginx-proxy ждёт ответа приложения 60 секунд. В шаблоне
`invoice-from-tasks` модель отвечала синхронно и дольше, поэтому таймаут для нашего домена
поднимает `make proxy-timeout` — после `make prod-up`, шаг в «Развёртывании» ниже. Протокол
`ai.engine` асинхронный (202 за 5 с, ответ — отдельным POST на `callbackUrl`, `docs/RESEARCH.md`),
так что долгий таймаут, вероятно, не понадобится; решится на этапе 2 `docs/PLAN.md`, а пока шаг
безвреден. Цель:
- берёт домен из `VIRTUAL_HOST` работающего контейнера приложения — того, что прокси обслуживает;
- находит контейнер nginx-proxy (не нашёлся или их несколько — `make proxy-timeout PROXY=<имя>`);
- дописывает `proxy_read_timeout 400s;` в его `/etc/nginx/vhost.d/<домен>_location`, сохраняя
  другие директивы; новый файл начинает с `default_location`, если он есть;
- перестраивает конфиг прямо в прокси (`docker-gen`, `nginx -t`, reload) — приложение не
  перезапускается — и проверяет, что файл подключён. Уже настроено — ничего не делает.

Предупредит, если `vhost.d` у прокси — не отдельный том: тогда настройка пропадёт, когда прокси
пересоздадут.

### Развёртывание

**DNS A-запись `aiconnect.bx-shef.by` должна указывать на сервер до подъёма** — иначе
сертификат не выпустится. На сервере нужны только два файла из репозитория и `.env`: образ
самодостаточный.

```bash
mkdir -p /home/bitrix/aiconnect && cd /home/bitrix/aiconnect

curl -fsSL -O https://raw.githubusercontent.com/bx-shef/aiconnect/main/docker-compose.prod.yml
curl -fsSL -O https://raw.githubusercontent.com/bx-shef/aiconnect/main/Makefile

umask 077   # .env и копии тома — только владельцу
cat > .env <<EOF
DOMAIN=aiconnect.bx-shef.by
# Ваш e-mail для Let's Encrypt или пусто (адреса на example.com Let's Encrypt отвергает).
LETSENCRYPT_EMAIL=
B24_TOKEN_ENC_KEY=$(openssl rand -hex 32)
# Заполнить после раздела 2 (кабинет разработчика Маркета):
B24_CLIENT_ID=
B24_CLIENT_SECRET=
B24_APP_CODE=
EOF
grep B24_TOKEN_ENC_KEY .env   # ⚠ сохраните ключ вне сервера (менеджер паролей)

make prod-up          # поднять контейнер (образ из GHCR)
make proxy-timeout    # таймаут прокси (см. выше); приложение не перезапускается
make ps               # через ~20 секунд — healthy
make health           # какие настройки заданы (без секретов); ключи и код — false до раздела 2
make doctor           # всё разом: контейнер, настройки, прокси, https, сертификат, Watchtower, диск
```

`make doctor` только читает. Каждая строка — ✓, ✗ (после «→» — что делать) или ⚠: проверить
нечем (нет `curl`, `openssl`, `df` не ответил). Есть ✗ —
команда завершается с ошибкой; только ⚠ — «ошибок нет, предупреждений: N». Что он проверяет:
- контейнер работает и здоров; `/api/health` изнутри — сборка и что не задано: в `.env` или в
  compose-файле. До раздела 2 он честно покажет ✗ «не задано в .env:
  B24_CLIENT_ID/B24_CLIENT_SECRET,B24_APP_CODE»;
- метка `keepalive=disabled` у контейнера; у прокси в `upstream` нашего домена есть рабочий
  сервер (иначе прокси не видит приложение — только заглушку `down`) и нет `keepalive`;
- таймаут прокси для домена подключён (`make proxy-timeout`);
- https снаружи отвечает и видит адрес клиента (`forwardedFor: used`); сертификат — как в
  браузере: доверенный, на наш домен, не истекает 14 дней (самоподписанная заглушка прокси до
  выпуска Let's Encrypt — ✗);
- Watchtower запущен; диск с каталогом данных docker (`docker info`) занят меньше чем на 90 %.

https он проверяет с самого сервера; если сервер не видит себя по внешнему адресу, проверьте с
другого компьютера: `curl -s https://aiconnect.bx-shef.by/api/health`. Так бывает за NAT: на
нашем сервере DNS указывает на входящий адрес, а исходящий другой — `make doctor` показывает
два ✗ (https по таймауту и «сертификат не прочитан»), хотя снаружи всё отвечает (2026-11-01).

**Сертификат не выпускается, в журнале acme-companion нет нашего домена** —
`docker logs <контейнер acme-companion> 2>&1 | tail`. Строка `could not get a nginx-proxy
container ID` значит, что companion потерял прокси (например, прокси пересоздали без метки
`com.github.nginx-proxy.nginx`) и не выпускает и не продлевает сертификаты никому на сервере.
Чинится в compose общего прокси: у сервиса acme-companion — `environment:
NGINX_PROXY_CONTAINER: <имя контейнера прокси>`, затем пересоздать только его
(`docker compose … up -d --no-deps <сервис>`). Перезапуск без этой правки не помогает.

**Keepalive к прокси выключен** меткой `com.github.nginx-proxy.nginx-proxy.keepalive=disabled`.
По умолчанию nginx-proxy держит соединения с приложением открытыми до 60 секунд, а Node закрывает
простаивающие через 5. Запрос в уже закрытое соединение получает `502`, и POST nginx не повторяет, а
Битрикс24 открывает страницы приложения именно POST-ом. Замер 2026-09-25: страница установки
открылась, `/app` сразу после неё — `502`.

`make` запускает compose без `DOMAIN`, `LETSENCRYPT_EMAIL` и `B24_TOKEN_ENC_KEY` из окружения
оболочки: иначе они побеждали бы `.env`, и экспортированный домен соседнего проекта увёл бы наш
сайт на чужой адрес. Источник один — `.env`.

`docker-compose.prod.yml` сам задаёт `NUXT_PUBLIC_SITE_URL=https://<DOMAIN>` и `TRUST_PROXY=1`
(nginx-proxy дописывает адрес клиента в `X-Forwarded-For`). Токены установки лежат в томе
`portals` (`/app/.data`): Watchtower пересоздаёт контейнер на каждом выкате, том это переживает.

**Обновления.** Образ — сам, через Watchtower. Какая сборка запущена, показывают `make doctor`
(«сборка») и `GET /api/health` (`commit`) — первые 7 знаков коммита, как в теге `sha-…`. Сравнивайте
с последним коммитом `main`, **который менял код**: мерж только документации, тестов, `Makefile`
или compose-файлов образ не собирает (`paths-ignore`), и сборка законно отстаёт от `main`.
`docker-compose.prod.yml` и `Makefile` Watchtower не трогает:
- новые цели — `make self-update`;
- новый compose — `make compose-update` покажет разницу с репозиторием и напечатает команду
  замены: `make compose-update CONFIRM=<sha256>` — sha256 именно показанного файла. Она заменит
  файл (копия прежнего — рядом, права прежние), затем `make prod-up`. Если между показом и заменой
  в `main` пришёл коммит, скачанное уже другое — отказ и новая разница. Файла ещё нет — поставит.
- из ветки, а не из `main`, — `REF=<ветка>` у обеих целей. `make -n self-update` только
  показывает команды.

**От чего защищает Makefile, а от чего нет.**
- Окружение общего хоста не влияет: `REF`, `PROXY`, `PROXY_TIMEOUT` и `CONFIRM` берутся только из
  командной строки `make`, а экспортированные соседями одноимённые переменные не действуют.
- Значения, которые вставляют как есть (`REF=<ветка>` из ссылки на PR, `CONFIRM=<sha256>` из вывода),
  берутся как текст и проверяются по формату до скачивания: кавычки, `;` и `$(…)` в них ничего не
  выполнят.
- ⚠ Сама командная строка make — это команды: `REF:=$(shell …)`, любая другая переменная с `$(…)`,
  `SHELL=…` выполнят что угодно. Не вписывайте в неё того, чего не понимаете.
- ⚠ **`MAKEFLAGS` в окружении** make считает той же командной строкой и разбирает до чтения Makefile.
  На сервере его быть не должно: проверка `env | grep MAKEFLAGS`; есть — `unset MAKEFLAGS` и найти,
  кто его экспортирует.

Список целей — `make help`.

**Откат** на известную версию: в `docker-compose.prod.yml` на сервере заменить `:latest` на
`:sha-<первые 7 знаков коммита>` (так тег ставит CI; список — на странице пакета) и `make prod-up`.
Watchtower следит за тегом из файла, поэтому, пока там `sha-…`, новые выкаты не приедут; вернуть
`:latest` — вернутся. Тот же приём — **пауза автообновлений**, например на время первых недель на
рабочем портале. ⚠ `make compose-update` с подтверждением вернёт `:latest` — в показанной разнице это видно.

**Копия тома с токенами** — `make backup` (файл в `./backups`). Токены в ней зашифрованы
`B24_TOKEN_ENC_KEY`: без ключа копия бесполезна, поэтому ключ хранится отдельно. Восстановить:

```bash
docker compose -f docker-compose.prod.yml exec -T app tar xzf - -C /app/.data < backups/portals-<дата>.tgz
docker compose -f docker-compose.prod.yml restart app
```

Потеряли том без копии — порталам нужно переустановить приложение: без токенов установщика не
узнаёт портал: запросы из его фрейма к нашему API получают отказ.

⚠ `TRUST_PROXY=1` верит `X-Forwarded-For` от любого адреса частной сети, а сеть `proxy-net` общая
для проектов хоста. Соседний контейнер на ней может назвать себя любым адресом и обойти лимиты
по IP (события установки, живые проверки фрейм-токена). Держите на `proxy-net` только свои проекты.

### Частые сбои

Сначала — `make doctor`: он называет большинство причин ниже сам.

| Что видно | Причина | Что делать |
|---|---|---|
| `502 Bad Gateway` в окне приложения, чаще при повторном открытии | прокси держит соединения с приложением (keepalive), а Node закрывает простаивающие через 5 с; POST из портала nginx не повторяет | `make compose-update` и команда с `CONFIRM=<sha256>` из её вывода (метка `keepalive=disabled`), `make prod-up`; в `make doctor` — ✓ «прокси ходит в приложение без keepalive» |
| `502` сразу после выката, через несколько секунд проходит | Watchtower пересоздаёт контейнер, Node ещё не слушает | подождать; повторяется — `make logs` |
| `504` примерно через минуту | прокси ждёт ответа 60 с, приложение отвечает дольше | `make proxy-timeout` |
| Запросы из фрейма к нашему API отвечают `503` | не задан `B24_APP_CODE` | код — на главной приложения у администратора; в `.env`, `make prod-up` |
| Установка падает с `500` или не сохраняется | нет `B24_TOKEN_ENC_KEY` или ключей `B24_CLIENT_ID`/`B24_CLIENT_SECRET` | `make doctor` назовёт переменную; в `.env`, `make prod-up`, переустановить |
| Браузер ругается на сертификат | A-запись домена не на этот сервер, Let's Encrypt отверг e-mail или лимит выпусков | `dig +short <домен>`; `docker logs` контейнера acme-companion; `LETSENCRYPT_EMAIL` — пусто или настоящий |
| Новая версия не приехала | мерж менял только документацию, тесты или `Makefile` — образ не собирается; Watchtower не запущен; в compose пин `sha-…` | «сборка» в `make doctor` против последнего коммита `main`, менявшего код; `make prod-redeploy` — не ждать Watchtower |

### Без nginx-proxy (локально или другой сервер)

`docker-compose.yml` собирает образ из исходников и публикует порт **только на
`127.0.0.1:3000`**: HTTPS и доступ снаружи даёт свой обратный прокси (nginx, Caddy, Traefik) на
этом же сервере, тогда `TRUST_PROXY=1`. Прокси на другой машине — замените на `"3000:3000"` и
закройте порт сетевым экраном: порт, доступный мимо прокси, позволяет обходить лимиты по IP.

```bash
cp .env.example .env               # заполнить (см. ниже)
docker compose up -d --build       # на сервере — в фоне
make build-local                   # локальная проверка: то же, но на переднем плане
```

Токены установки — в томе `portals` (`/app/.data`). Без тома пересоздание контейнера их потеряет,
и сервер перестанет узнавать порталы до переустановки приложения.

### Переменные окружения

Полный шаблон с комментариями — `.env.example`.

| Переменная | Зачем | Без неё |
|---|---|---|
| `DOMAIN` (прод) | домен для nginx-proxy и сертификата; из него `docker-compose.prod.yml` собирает `NUXT_PUBLIC_SITE_URL` | compose не поднимется |
| `NUXT_PUBLIC_SITE_URL` | адрес для обработчика событий; в проде задаётся из `DOMAIN` | установка возьмёт адрес из браузера |
| `B24_CLIENT_ID`, `B24_CLIENT_SECRET` | сверка установки и обновление токена установщика | установка **не сохраняется** (`docs/B24_EVENTS.md`) — сервер не узнаёт порталы |
| `B24_TOKEN_ENC_KEY` | шифрование токенов установки — access и refresh (`openssl rand -hex 32`) | установка падает с `500` |
| `B24_APP_CODE` | принимать фрейм-токены только своего приложения; код показывает администратору главная страница приложения, пока переменная не задана | **`503` на все запросы из фрейма** к нашему API |
| `TRUST_PROXY` | `1` — сервер за обратным прокси: лимиты считаются по IP клиента; в проде уже `1` | лимиты по IP общие для всех, кто за прокси (адрес прокси один) |
| `B24_SPY_PORTALS` | порталы, где работает шпион протокола (этап 1), через запятую | шпион выключен везде: страница говорит «выключен», `completions_url` шпиона — `404` |
| `B24_SPY_FULL` | `1` — полный журнал шпиона для порталов из `B24_SPY_PORTALS`: тела запросов целиком (до 500 запросов и 50 МБ на портал), выгрузка JSON; только на своём стенде | строки обрезаны до 500 знаков, журнала и выгрузки нет |
| `B24_APPLICATION_TOKEN` | фиксированный `application_token`; для приложения из Маркета — **пустой** (у каждого портала свой) | первый `ONAPPINSTALL` задаёт токен портала |
| `B24_SELFHOSTED_HOSTS` | коробочные порталы вне `*.bitrix24.*` для SSRF-гарда | к ним сервер не пойдёт |
| `B24_SPY_BOX_APP` | коробка-стенд шпиона: `<хост> <client_id> <client_secret> <код приложения>` её локального приложения, через пробел, в значениях пробелов нет; хост — и в `B24_SELFHOSTED_HOSTS`, и в `B24_SPY_PORTALS` | с коробки установка не проходит сверку; задана с ошибкой — для её хоста `503`, `spyBox: invalid` в health и `[spy-box]` в `make logs` |

⚠ **Копия `B24_TOKEN_ENC_KEY` — вне сервера** (менеджер паролей, хранилище секретов). Потеря или
смена ключа делает сохранённые токены нечитаемыми: сервер перестанет узнавать порталы до
переустановки приложения. Ротации ключа пока нет (`server/utils/secretCrypto.ts`).

### Пределы запросов

`server/middleware/requestLimits.ts`, значения — `server/utils/requestLimits.ts`:
- тело POST к `/api`: события портала — до 64 КБ, остальное — до 512 КБ; больше — `413`;
- без заголовка `Content-Length` — `411` (тело неизвестной длины пришлось бы читать целиком).
  Браузер и портал его шлют; ⚠ для событий портала это проверяется после выката
  (`docs/project-map.md`);
- события установки и удаления — до 60 в минуту с одного адреса (IPv6 — с сети /64), `429`;
  прочие события не считаются: они ничего не стоят, а иначе чужой портал мог бы выжечь лимит и
  заблокировать чужие установки;
- сверки установки — до 600 в минуту всего: каждая — исходящий запрос к серверу авторизации с
  нашими `client_id`/`client_secret`; мусор и удаления этот потолок не тратят;
- живые проверки фрейм-токена — до 60 в минуту с одного адреса (IPv6 — с /64), `429`.

HTTPS обычно даёт обратный прокси перед контейнером — тогда `TRUST_PROXY=1`, иначе все запросы
выглядят пришедшими с адреса прокси. Берётся **последний** адрес `X-Forwarded-For` (его дописывает
прокси), поэтому схема рассчитана на один прокси. Заголовку верим, только если соединение пришло
из частной сети (свой прокси, мост Docker): клиент из интернета подставить себе адрес не сможет.
Проверка: `curl -s https://<адрес>/api/health` через прокси — в ответе `request.forwardedFor`
должно быть `used`; `ignored` — заголовку не верим (нет `TRUST_PROXY=1` или прокси ходит к
приложению не из частной сети), и все клиенты делят лимиты адреса прокси.

## 2. Приложение в Маркете

Приложение регистрирует владелец в кабинете разработчика Битрикс24 Маркетплейс и ставит на
тестовый портал кнопкой «Протестировать» — до модерации и публикации. Порядок — по статье
документации «Как добавить решение в кабинет разработчика» и «Мастер установки тиражного
приложения» (MCP `b24-dev-mcp`):

1. «Мои приложения» → «Добавить приложение» → регион → «Создать».
2. Технические характеристики:

   | Поле | Значение |
   |---|---|
   | Разделы системы (скоупы) | `ai_admin`, `user_brief` (`docs/REST_METHODS.md`, «Права приложения») |
   | Добавлять свою страницу и пункт в главном меню | да — у приложения есть главная `/app` |
   | Встраивать виджеты в интерфейс | нет |
   | Может устанавливать любой пользователь | нет — ставит администратор (`ai.engine.register` — только администратор) |
   | Тип приложения, минимальный тариф | на ваше усмотрение: нужны облачный Битрикс24 (провайдеры `ai.engine` в коробке недоступны — `docs/RESEARCH.md`) и REST |
   | Ссылка на приложение | `https://aiconnect.bx-shef.by/app` |
   | Ссылка на установочное приложение | `https://aiconnect.bx-shef.by/install` |

   Названия полей — из документации; в кабинете формулировки могут чуть отличаться.
3. **Код приложения** — вверху справа в карточке: `<код партнёра>.<код>`. Вторую часть можно
   менять только до первой положительной модерации. Это `B24_APP_CODE`.
4. **«Протестировать»**: там ключи `client_id` и `secret_id` — это `B24_CLIENT_ID` и
   `B24_CLIENT_SECRET`, и поле адреса портала — **тестовый портал**. Откроется карточка решения
   на портале с кнопкой «Установить».
5. Ключи и код — в `.env` на сервере, затем `make prod-up` (контейнер пересоздастся с ними).
   `B24_APPLICATION_TOKEN` не задавать.

Установку, удаление и переустановку проверяем сами — этого требует и модерация.

Пока `B24_APP_CODE` не задан, главная страница приложения (`/app`) показывает администратору
портала код из `app.info` и список того, что не настроено на сервере (по `GET /api/health`). До
этого запросы из фрейма к нашему API отвечают `503`.

### Без Маркета: локальное приложение своего портала

В карточке локального приложения: «Путь обработчика» — `https://<адрес>/app`, «Путь для
первоначальной установки» — `https://<адрес>/install` (название поля — из статьи «Мастер установки
локального приложения»), те же права, режим «только API» выключен. Ключи `client_id` и
`client_secret` портал выдаст после сохранения.

## 3. Установка — проверка этапа 0

1. Установить приложение (кабинет Маркета → «Протестировать» → «Установить» на тестовом портале) —
   откроется `/install`: проверит права (`ai_admin`, `user_brief`), подпишется на события,
   завершит установку. Недостающие права покажет списком.
2. Проверить, что сервер готов: `GET /api/health` → все флаги `config` (кроме `trustProxy`
   без прокси) — `true`.
3. Проверить, что установка сохранилась: `make logs` — информационная строка об установке с
   `member_id` портала (`docs/B24_EVENTS.md`, «Журнал»), без отказов сверки.
4. «Приложения» → aiconnect: главная открывается во фрейме; администратор без проблем сервера не
   видит блока «Сервер приложения настроен не полностью».
5. Удалить приложение и поставить снова: в журнале — удаление, затем установка.

## 4. Шпион протокола (этап 1)

0. В `.env` на сервере — `B24_SPY_PORTALS=<домен тестового портала>` (например,
   `b24-ypkv9c.bitrix24.by`), затем `make prod-up`. Без этого шпион выключен везде: он хранит
   фрагменты запросов пользователей, поэтому только на своих тестовых порталах.
1. «Приложения» → aiconnect → «Шпион протокола» (кнопка видна администратору) → «Зарегистрировать
   все». В таблице все шесть категорий — «зарегистрирован». Ошибка
   `ENGINE_REGISTER_ERROR_COMPLETIONS_URL_FAIL` значит, что портал не достучался GET-запросом до
   `https://<домен>/api/engine/…` — проверьте `curl -s https://<домен>/api/health` снаружи.
2. Сценарии и что записывать — `docs/PROTOCOL.md`. Запросы видны на той же странице
   («Обновить»); в `make logs` — строки `[engine] <member_id> <категория> <размер>B keys=…`
   (`scenario=…`, `full` — если заданы), без текстов.
   **Полный текст** — `B24_SPY_FULL=1` в `.env`, затем `make prod-up`; на странице шпиона
   «Полный текст: вкл». ⚠ Отдельного стенда сейчас нет: сервер `aiconnect.bx-shef.by` один, и
   флаг включает журнал на нём — защита только список `B24_SPY_PORTALS`, держите в нём **только
   свои тестовые порталы**. Журнал лежит в томе `portals`; в `make backup` он **не попадает** (в нём
   тексты открытым текстом, восстанавливать его незачем). Тела больше 1 МБ режет прокси
   (п. 3), в журнал они не попадут.
3. ⚠ **Размер тела.** Приложение принимает до 16 МБ, но у nginx-proxy по умолчанию
   `client_max_body_size 1m`: запрос больше 1 МБ (например, `audio` с файлом внутри, если он
   приходит так) получит от прокси `413` и до шпиона не дойдёт — ни на странице, ни в журнале его
   не будет. Если `audio`/`call` не появляются, посмотрите журнал прокси
   (`docker logs nginx-proxy 2>&1 | grep engine`) и при `413` допишите
   `client_max_body_size 16m;` в тот же файл `vhost.d/<домен>_location`, что и таймаут
   (`make proxy-timeout` его создаёт), и перезагрузите прокси.
4. После прогона — «Снять все».

### Коробка-стенд (bx-shef/toolsai-stand)

На стенде ещё не проверено — первый прогон покажет.

1. Стенд виден снаружи по https (`./stand.sh public`, адрес CloudPub) и зарегистрирован в облаке
   Битрикс24 (OAuth коробки идёт через `oauth.bitrix.info`).
2. На стенде — локальное приложение («Разработчикам» → «Другое» → «Локальное приложение»): путь
   обработчика `https://aiconnect.bx-shef.by/app`, установки — `/install`, права `ai_admin`,
   `user_brief`, `telephony`, `crm`. Код приложения (`local.…`), `client_id` и `client_secret` — в
   `.env` сервера одной строкой: `B24_SPY_BOX_APP=<хост стенда> <client_id> <client_secret> <код>`;
   хост стенда (без схемы и порта) — в `B24_SELFHOSTED_HOSTS` и в `B24_SPY_PORTALS`. Затем
   `make prod-up`; в `make health` — `spyBox: on` (`invalid` — причина в `make logs`, строка
   `[spy-box]`), и установка. Сервер у нас один, он же боевой: после прогонов строку
   `B24_SPY_BOX_APP` и хост стенда из обоих списков убрать, `make prod-up`.
3. Движки: на коробке нет REST `ai.engine.register`, кнопка «Зарегистрировать все» не сработает.
   Адреса — на странице шпиона, «Адреса completions_url» (не публиковать: по адресу можно слать
   запросы в шпион этого портала); регистрация — в контейнере стенда. Имя сервиса `portal` и
   корень `/var/www/html` — из bx-shef/toolsai-stand (`docker-compose.yml`):
   ```bash
   docker compose exec portal php -r '
     $_SERVER["DOCUMENT_ROOT"] = "/var/www/html";
     require "/var/www/html/bitrix/modules/main/include/prolog_before.php";
     \Bitrix\Main\Loader::includeModule("ai");
     foreach (["text" => "<адрес text>", "audio" => "<адрес audio>"] as $c => $url) {
       var_dump(\Bitrix\AI\ThirdParty\Manager::register(["name" => "TEST $c", "code" => "sh_aiconnect_spy_$c", "category" => $c, "completions_url" => $url, "settings" => []]));
     }'
   ```
   Остальные категории — так же. Снять — `Manager::unRegister(["code" => "sh_aiconnect_spy_<категория>"])`.
   Так же движки регистрирует `shef.toolsai` (`lib/engine/registrar.php`). На коробке audio-движок
   виден CRM только при зарегистрированном text-движке (`ThirdParty::hasQuality()`).
   Таблица «Провайдеры» на коробке покажет ошибку `ai.engine.list` (того REST там тоже нет) —
   пойманные запросы, журнал и выгрузка работают.

## Смена адреса сервера

Переустановите приложение (или откройте `/install` из портала): установка снимет
подписки на события со старым адресом (`event.unbind`) и оформит новые. Если приложение уже
установлено, `installFinish` не вызывается — страница только обновит подписки. Когда появятся
провайдеры BitrixGPT, их `completions_url` тоже придётся перерегистрировать (этапы 1–3).
