# События портала

> Last reviewed: 2026-09-24

Контракт входящих событий Битрикс24. Обработчик — `server/api/b24/events.post.ts` (тонкая
обёртка), решение — `server/utils/b24EventsHandler.ts` (покрыт `tests/server/b24EventsHandler.test.ts`),
разбор и проверки — `server/utils/b24Events.ts`, `server/utils/verifyInstallMember.ts`, хранилище —
`server/utils/tokenStore.ts`. Схема перенесена из эталона `client-bank-alfa-by`.

## Подписки

Оформляет страница установки (`app/pages/install.vue`) методом `event.bind` **до**
`installFinish` — иначе `ONAPPINSTALL` не придёт. Адрес — `<NUXT_PUBLIC_SITE_URL>/api/b24/events`.

| Событие | Что делаем |
|---|---|
| `ONAPPINSTALL` | сохраняем домен, токены установщика и `application_token` |
| `ONAPPUNINSTALL` | стираем всё, что знаем о портале |

## Зачем нам токены установки

Только для записи ставок **не-администратором** из списка редакторов: `app.option.set` доступен
лишь администратору (`docs/SETTINGS.md`). Установку приложения делает администратор — его токен
и сохраняем. И ещё для проверки, что запрос к нашему API пришёл с портала, где приложение
установлено (`server/utils/frameAuth.ts`).

## Проверки

Тело — PHP-скобочная форма (`auth[member_id]=…`), разбирается без записи в прототип объекта.

**`application_token`** (fail-closed, сравнение за постоянное время):
- установка: если задан `B24_APPLICATION_TOKEN` — сверяем с ним; иначе первый непустой токен
  становится токеном портала. Сохранённый токен **не перезаписывается** переустановкой;
- удаление: нужен ожидаемый токен (окружение или сохранённый); нет ни того, ни другого — `503`,
  чужой — `403`.

**member_id при установке.** `member_id` в событии присылает клиент, а `application_token` у
злоумышленника, установившего приложение на свой портал, тоже есть. Поэтому присланный
refresh-токен обновляется на сервере авторизации портала: ответ несёт настоящий
`member_id` гранта, и он обязан совпасть с заявленным (`403` — не совпал или грант поддельный,
`503` — проверить сейчас нельзя). Обновление ротирует токен — сохраняется **вернувшийся** грант.

**Сервер авторизации** — тот, что портал назвал в `auth[server_endpoint]` («Адрес сервера
авторизации для обновления токена» — документация события), но только из белого списка
(`server/utils/b24Host.ts → resolveOAuthHost`): облачные `oauth.bitrix24.tech` (текущая
документация) и `oauth.bitrix.info` (прежний адрес, на него ходили эталоны; возможно, на нём
порталы других зон). Поля нет — `oauth.bitrix24.tech`. Сервер сохраняется в записи о портале, и
токен установщика потом продлевается там же. Не из списка — `403`, в журнал ошибок.

⚠ **Коробка сервером авторизации не бывает**, даже из `B24_SELFHOSTED_HOSTS`: коробка ручается
за свой домен, но `member_id` в её «гранте» может быть любым — её владелец перезаписал бы запись
облачного портала-жертвы, а наш `client_secret` ушёл бы ему в запросе продления (находка
`/code-review`). Приложение облачное: установка из коробки не сохраняется.

**Домен при установке** сверяется так же: настоящий домен гранта — хост `client_endpoint` из
ответа OAuth — документация называет его «адрес REST-интерфейса портала». ⚠ Поле `domain`
того же ответа — хост сервера авторизации, не портала: по нему сверять нельзя. Эталон сверял только
`member_id`, и `/code-review` нашёл обход: свой `member_id` и свой грант (сверка проходит), но
`auth[domain]` жертвы — индекс «домен → портал» указал бы на запись злоумышленника, и запросы
из фрейма жертвы проверялись бы по ней. Сохраняется домен **из гранта**. Нет `member_id` или
`client_endpoint` в ответе — `503` («не можем проверить»), а не «примем». Формат
`https://<портал>/rest/` — из примера документации; на живом портале — проверить после выката
(`docs/project-map.md`).

⚠ **Без `B24_CLIENT_ID`/`B24_CLIENT_SECRET` установка не сохраняется** (`503`). Замер
2026-09-24 на собранном сервере: без сверки повторная «установка» с тем же `member_id` и чужими
токенами перезаписывала токены портала (сохранённый `application_token` при этом устоял).
Эталон в этом случае деградирует до проверки одного токена; здесь выбрано fail-closed — без
реквизитов токен всё равно не обновить.

**Домен** проходит SSRF-гард (`server/utils/b24Host.ts`): только `*.bitrix24.<зона>` и коробки
из `B24_SELFHOSTED_HOSTS`. Дальше везде — нормализованный хост из гарда, а не сырой ввод.

**Пределы.** Тело события — до 64 КБ, обязателен `Content-Length` (`server/middleware/requestLimits.ts`).
События установки и удаления — не больше 60 в минуту с одного адреса (IPv6 — с сети /64:
одному клиенту обычно выдают целую /64); считаются только они — поток посторонних событий,
который любой портал может направить на наш адрес, лимит не тратит. Сверок установки (запросов
к серверу авторизации с нашими `client_id`/`client_secret`) — не больше 600 в минуту всего; этот
потолок списывается прямо перед запросом, после всех проверок, — мусор и удаления его не тратят,
иначе поток мусора блокировал бы настоящие удаления (находки `/code-review`,
`server/utils/requestLimits.ts`).

**Журнал.** Отказы, на которые должен сработать мониторинг (нет реквизитов OAuth, сервер
авторизации не из списка, установка не прошла сверку, исчерпан потолок сверок), пишутся в журнал
ошибок (`console.error`), а обычные установки и удаления — в информационный.

## Что хранится

`useStorage('portals')` (fs-драйвер Nitro, `.data/portals`, в Docker — том):
`portal:<member_id>` → домен, access-токен и refresh-токен (оба — AES-256-GCM, ключ
`B24_TOKEN_ENC_KEY`), срок, `application_token`, сервер авторизации; `domain:<домен>` → `member_id`.
Удаление приложения стирает обе записи; чужой индекс домена (домен перешёл к другому порталу)
не трогается ни при удалении, ни при переезде. Индекс, указывающий на запись с другим доменом,
считается устаревшим. Токены и тела запросов в журнал не пишутся — только `member_id`.

## Известные ограничения (приняты осознанно)

- **Индекс домена — «прочитал, сравнил, удалил» без блокировки** (`tokenStore.ts →
  removeDomainIfOwned`). Если ровно между сравнением и удалением тот же домен займёт новая
  установка другого портала, её свежий индекс может пропасть — портал получит «не установлено» до
  переустановки. Нужны две настоящие установки на один домен в одну миллисекунду; сервер один, и
  хранилище не даёт атомарной операции «сравни и удали». Отмечено ревьюерами панели.

## Проверено на собранном сервере (2026-09-24)

Без живого портала, запросами к `node .output/server/index.mjs`:
- установка с нелегальным доменом — `400`;
- удаление без сохранённого токена — `503`, с чужим токеном — `403`, со своим — запись стёрта;
- переустановка с чужим `application_token` не меняет сохранённый.

Живая проверка с порталом — после выката (`docs/project-map.md`).
