# Архитектура

> Last reviewed: 2026-09-26

Как устроено приложение и почему так. Правила расчёта — `docs/PROCESSING.md`, настройки —
`docs/SETTINGS.md`, вызовы REST — `docs/REST_METHODS.md`.

## Стек

Nuxt 4 (SPA, `ssr: false`) + `@bitrix24/b24ui-nuxt` (интерфейс) + `@bitrix24/b24jssdk` (REST из
фрейма и с сервера) + Nitro (наш `/api`) + `openai` (транспорт к BitrixGPT). Как в эталонах
`client-bank-alfa-by` и `ai-price-import`.

**Один артефакт.** В эталоне client-bank статика отдаётся nginx, а backend — отдельно. Здесь
серверной работы мало, поэтому один Nitro-сервер отдаёт и страницы, и `/api`. Проверено на
сборке: сервер отвечает `200` и на `GET`, и на `POST` к страницам — Битрикс24 открывает
обработчики POST-запросом, и отдельный трюк nginx (`error_page 405 =200`) не нужен.

Что nginx эталона делал попутно, у нас делает Nitro или общий прокси (сверено 2026-09-25):
- кэш скриптов и стилей `/_nuxt` на год (`immutable`) — Nitro по умолчанию;
- сжатие — `nitro.compressPublicAssets`: `.gz` и `.br` при сборке, самый большой скрипт — 234 КБ →
  62 КБ; общий nginx-proxy сам не сжимает;
- соединения к Node без keepalive — метка `keepalive=disabled` в `docker-compose.prod.yml`: nginx
  эталона держал соединение дольше прокси, а без него прокси ловил закрытые Node соединения —
  `502` на POST из портала;
- таймаут долгих ответов — `make proxy-timeout` для нашего домена;
- лимиты запросов — в самом приложении (`server/utils/requestLimits.ts`, `rateLimit.ts`).

**SPA, а не SSR.** Все рабочие страницы живут во фрейме портала, SEO им не нужно; SPA
избавляет от гидрации с редиректами. Настройки окружения (`NUXT_PUBLIC_SITE_URL`) подхватываются
при запуске — проверено на сборке, пересборка образа под другой адрес не нужна.

**Выкат — как в client-bank.** `main` → образ в GHCR → Watchtower на сервере → общий nginx-proxy с
TLS Let's Encrypt, адрес `https://invoice-from-tasks.bx-shef.by` (`docs/DEPLOY.md`). Образ один
на любой сервер; единственный build-arg — коммит сборки для `GET /api/health`. Проверка сервера
одной командой — `make doctor`.

## Страницы (`app/pages/`)

| Путь | Когда открывается | Что делает |
|---|---|---|
| `/` | прямая ссылка | публичное описание приложения |
| `/install` | установка приложения в портал | права, встройка, подписки на события, `installFinish` |
| `/app` | «Приложения» → «Счёт из задач» | состояние настроек, как пользоваться, вход в настройки |
| `/settings` | из `/app` | общие, ставки, наценки, промпты, доступ, хранилище |
| `/invoice` | карточка счёта → верхняя кнопка → «Заполнить из задач» | выбор источника и типа, предпросмотр, запись, консультации |

Все, кроме `/`, обёрнуты в `InPortalGate`: вне фрейма показывают «откройте в Битрикс24».

## Слои

```
shared/domain/     чистые правила: время, ставки, наценки по тегам, пересчёт валюты, сборка
                   строк, настройки, промпты, бюджет места — общие для страниц и сервера,
                   покрыты тестами
app/utils/         чистые помощники страниц, покрыты тестами: установка, контекст встройки,
                   замер места, свежесть токена фрейма (frameToken), параллельные чтения
                   (concurrency), сбор страниц (paging), разбор пакета (b24Batch), итог
                   записи в счёт (writeOutcome), что не настроено на сервере (serverHealth),
                   названия единиц измерения (measures)
app/composables/   связь с порталом и сервером: useB24 (фрейм, REST v2 и v3), useApi (наш
                   /api), useAppSettings, useInvoiceFill (сценарий счёта), useCatalog
                   (единицы измерения), useUsers, useStorageProbe (замер места)
app/components/    интерфейс на b24ui
server/api/        наш API: события портала, запись настроек и ставок, BitrixGPT — тонкие
                   обёртки: решение принимают чистые модули server/utils (b24EventsHandler,
                   optionWrites, aiRequests, installerCall), покрытые тестами
server/middleware/ заголовки страниц (CSP) и пределы запросов к /api
server/utils/      проверка фрейм-токена, SSRF-гард, хранилище токенов, клиент REST, LLM,
                   пределы запросов
```

## Кто и какими правами ходит в портал

| Действие | Откуда | Чьими правами |
|---|---|---|
| Чтение счёта, задач (с тегами, v2), результатов задач (REST v3), времени, курсов валют, единиц измерения; запись товаров и дела в счёт | фрейм | сотрудник, открывший окно |
| Чтение настроек | фрейм | сотрудник (разрешено всем) |
| Запись общих настроек | сервер | администратор (его фрейм-токен) |
| Запись ставок | сервер | администратор — своим токеном; редактор — токеном установщика |
| Замер места | фрейм | администратор |

Ключевое свойство: товары в счёт пишет **сотрудник своими правами** — приложение не расширяет
его доступ к CRM. Токен установщика используется в одном месте — запись ставок редактором.

## Безопасность сервера

- **Кто пришёл** (`server/utils/frameAuth.ts`): `Authorization: Bearer <фрейм-токен>` и
  `X-B24-Domain`. Домен — через SSRF-гард; портал обязан быть в хранилище установок (иначе ключ
  BitrixGPT был бы открыт любому порталу); токен проверяется вызовом `profile` и `app.info.CODE`
  (фрейм-токен чужого приложения на том же портале тоже прошёл бы `profile`). `B24_APP_CODE`
  обязателен: без него — `503`, а не пропуск проверки. Решение кэшируется на минуту по хэшу
  токена (полный кэш вытесняет старые записи, а не сбрасывается целиком); живых проверок — не
  больше 60 в минуту с одного IP (поток случайных токенов иначе гонял бы сервер в чужие порталы).
- **BitrixGPT** (`server/utils/aiGateway.ts`, `aiRequests.ts`): ключ только на сервере; промпты
  берутся из настроек портала, а не из запроса; лимит — в двух измерениях: 120 запросов и 3000
  строк счёта на сотрудника за 10 минут, 1200 запросов и 30 000 строк на портал за час,
  консультация весит 25 строк (в памяти процесса — при нескольких экземплярах нужен общий
  счётчик); сырой текст провайдера наружу не отдаётся.
- **Установка** — `docs/B24_EVENTS.md`: `member_id` и домен сверяются с OAuth-грантом на
  облачном сервере авторизации портала (из белого списка; коробка сервером авторизации не
  бывает); оба токена установщика хранятся зашифрованными (AES-256-GCM). Токен установщика
  читается заново на каждый вызов, вызовы одного портала идут по очереди с таймаутом 60 с
  (`installerCall.ts`) — refresh-токен одноразовый, а зависший запрос не должен блокировать портал.
- **Пределы запросов**: тело POST к `/api` — до 64 КБ (события) и 512 КБ (остальное), без
  `Content-Length` — `411` (`server/middleware/requestLimits.ts`); события установки и удаления —
  до 60 в минуту с адреса (IPv6 — с /64), посторонние события не считаются; сверок установки —
  до 600 в минуту всего, списывается перед запросом к серверу авторизации (`b24EventsHandler.ts`).
  IP за прокси — последний адрес `X-Forwarded-For` при `TRUST_PROXY=1` и только от соединений из
  частной сети; `/api/health` показывает, учтён ли заголовок (`docs/DEPLOY.md`). Счётчики чистятся
  по окну каждого ключа и ограничены 20 000 ключей (`rateLimit.ts`) — поток с тысяч адресов не
  съест память и процессор.
- **Запись в портал из фрейма** — без автоповторов SDK при сетевых сбоях (`app/config/b24.ts →
  sdkRestrictionParams`): запрос, выполненный порталом с опоздавшим ответом, иначе ушёл бы ещё
  раз — дубли строк счёта, дел и пунктов меню.
- **Заголовки страниц** (`server/middleware/securityHeaders.ts`): `frame-ancestors` только для
  порталов Битрикс24; `X-Frame-Options` не ставится — он запретил бы и портал.

## Токен фрейма

SDK обновляет токен только на пути своих запросов. Токен уходит и на наш сервер, поэтому
`useApi` перед запросом обновляет его, если жить ему меньше минуты
(`app/utils/frameToken.ts`). Опция `keepAuthFresh` из документации b24jssdk в установленной
версии 2.2.0 отсутствует — проверено по типам пакета.
