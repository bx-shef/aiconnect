# Архитектура

> Last reviewed: 2026-09-28

Как устроено приложение и почему так. Вызовы REST — `docs/REST_METHODS.md`, протокол
`ai.engine.register` — `docs/RESEARCH.md`, этапы — `docs/PLAN.md`.

**Состояние — этап 0 плана:** каркас без предметной части. Приложение ставится в портал, сохраняет
токены установки и показывает администратору, что не настроено на сервере. Провайдеров BitrixGPT
оно пока не регистрирует и запросов модели не обслуживает — это этапы 1–3.

## Стек

Nuxt 4 (SPA, `ssr: false`) + `@bitrix24/b24ui-nuxt` (интерфейс) + `@bitrix24/b24jssdk` (REST из
фрейма и с сервера) + Nitro (наш `/api`). Вызов моделей провайдеров — Vercel AI SDK, появится на
этапе 2.

**Один артефакт.** Один Nitro-сервер отдаёт и страницы, и `/api`. Проверено на сборке шаблона:
сервер отвечает `200` и на `GET`, и на `POST` к страницам — Битрикс24 открывает обработчики
POST-запросом, и отдельный трюк nginx (`error_page 405 =200`) не нужен. Тот же сервер будет
принимать запросы BitrixGPT на `completions_url` (этап 1).

Что в эталоне client-bank делал свой nginx, у нас делает Nitro или общий прокси (сверено 2026-09-25):
- кэш скриптов и стилей `/_nuxt` на год (`immutable`) — Nitro по умолчанию;
- сжатие — `nitro.compressPublicAssets`: `.gz` и `.br` при сборке; общий nginx-proxy сам не сжимает;
- соединения к Node без keepalive — метка `keepalive=disabled` в `docker-compose.prod.yml`: иначе
  прокси ловил закрытые Node соединения — `502` на POST из портала;
- таймаут долгих ответов — `make proxy-timeout` для нашего домена;
- лимиты запросов — в самом приложении (`server/utils/requestLimits.ts`, `rateLimit.ts`).

**SPA, а не SSR.** Все рабочие страницы живут во фрейме портала, SEO им не нужно; SPA
избавляет от гидрации с редиректами. Настройки окружения (`NUXT_PUBLIC_SITE_URL`) подхватываются
при запуске — пересборка образа под другой адрес не нужна.

**Выкат — как в client-bank.** `main` → образ в GHCR → Watchtower на сервере → общий nginx-proxy с
TLS Let's Encrypt, адрес `https://aiconnect.bx-shef.by` (`docs/DEPLOY.md`). Образ один на любой
сервер; единственный build-arg — коммит сборки для `GET /api/health`. Проверка сервера одной
командой — `make doctor`.

## Страницы (`app/pages/`)

| Путь | Когда открывается | Что делает |
|---|---|---|
| `/` | прямая ссылка | публичное описание приложения |
| `/install` | установка приложения в портал | права, подписки на события, `installFinish` |
| `/app` | «Приложения» → aiconnect | что это; администратору — что не настроено на сервере |

`/install` и `/app` обёрнуты в `InPortalGate`: вне фрейма показывают «откройте в Битрикс24».

## Слои

```
app/config/b24.ts  права, события, настройки SDK — одно место
app/utils/         чистые помощники страниц, покрыты тестами: установка (install), свежесть
                   токена фрейма (frameToken), что не настроено на сервере (serverHealth)
app/composables/   useB24 (фрейм, REST v2), useApi (наш /api с фрейм-токеном)
app/components/    InPortalGate
server/api/        b24/events (установка и удаление), health — тонкие обёртки: решение
                   принимают чистые модули server/utils (b24EventsHandler), покрытые тестами
server/middleware/ заголовки страниц (CSP) и пределы запросов к /api
server/utils/      проверка фрейм-токена (frameAuth), SSRF-гард (b24Host), хранилище токенов
                   (tokenStore + secretCrypto), клиент REST (b24Client), разбор событий
                   (b24Events), сверка установки (verifyInstallMember), пределы запросов
                   (requestLimits, rateLimit), коммит сборки (buildInfo)
```

`shared/` сейчас нет: общих для страниц и сервера правил этапу 0 не нужно. Алиас `#shared`
оставлен — он встроен в Nuxt.

## Кто и какими правами ходит в портал

| Действие | Откуда | Чьими правами |
|---|---|---|
| Проверка прав, подписка на события, `installFinish` | фрейм `/install` | администратор, устанавливающий приложение |
| `profile`, `app.info` на главной | фрейм `/app` | сотрудник, открывший окно |
| Проверка фрейм-токена (`profile`, `app.info`) | сервер | токен того же сотрудника |

Токены установщика сохраняются на сервере при `ONAPPINSTALL` (`docs/B24_EVENTS.md`); на этапе 0
сервер ими в портал не ходит.

## Безопасность сервера

- **Кто пришёл** (`server/utils/frameAuth.ts`, обвязка — `requestContext.ts → requireFrameUser`):
  `Authorization: Bearer <фрейм-токен>` и `X-B24-Domain`. Домен — через SSRF-гард; портал обязан
  быть в хранилище установок; токен проверяется вызовом `profile` и `app.info.CODE` (фрейм-токен
  чужого приложения на том же портале тоже прошёл бы `profile`). `B24_APP_CODE` обязателен: без
  него — `503`, а не пропуск проверки. Решение кэшируется на минуту по хэшу токена; живых
  проверок — не больше 60 в минуту с одного IP. На этапе 0 ни один обработчик `requireFrameUser`
  не зовёт — он понадобится настройкам (этап 3).
- **Установка** — `docs/B24_EVENTS.md`: `member_id` и домен сверяются с OAuth-грантом на
  облачном сервере авторизации портала (из белого списка; коробка сервером авторизации не
  бывает); оба токена установщика хранятся зашифрованными (AES-256-GCM, `secretCrypto.ts`).
- **Пределы запросов**: тело POST к `/api` — до 64 КБ (события) и 512 КБ (остальное), без
  `Content-Length` — `411` (`server/middleware/requestLimits.ts`); события установки и удаления —
  до 60 в минуту с адреса (IPv6 — с /64), посторонние события не считаются; сверок установки —
  до 600 в минуту всего, списывается перед запросом к серверу авторизации (`b24EventsHandler.ts`).
  IP за прокси — последний адрес `X-Forwarded-For` при `TRUST_PROXY=1` и только от соединений из
  частной сети; `/api/health` показывает, учтён ли заголовок (`docs/DEPLOY.md`). Счётчики в памяти
  процесса (один экземпляр сервера; при нескольких нужен общий), чистятся по окну каждого ключа и
  ограничены 20 000 ключей (`rateLimit.ts`).
- **Запись в портал из фрейма** — без автоповторов SDK при сетевых сбоях (`app/config/b24.ts →
  sdkRestrictionParams`): запрос, выполненный порталом с опоздавшим ответом, иначе ушёл бы ещё
  раз — дубли подписок, а дальше и регистраций провайдеров.
- **Заголовки страниц** (`server/middleware/securityHeaders.ts`): `frame-ancestors` только для
  порталов Битрикс24; `X-Frame-Options` не ставится — он запретил бы и портал.
- **Впереди (этап 2, `docs/PLAN.md`)**: подлинность запросов на публичный `completions_url`,
  SSRF через `callbackUrl` из запроса, шифрование API-ключей клиентов, ни ключей, ни текстов в
  журналах.

## Токен фрейма

SDK обновляет токен только на пути своих запросов. Токен уходит и на наш сервер, поэтому
`useApi` перед запросом обновляет его, если жить ему меньше минуты
(`app/utils/frameToken.ts`). Опция `keepAuthFresh` из документации b24jssdk в установленной
версии 2.2.0 отсутствует — проверено по типам пакета.
