# Смок-прогон на тестовом портале

> Last reviewed: 2026-09-26

`pnpm smoke` — живая проверка REST и BitrixGPT на **тестовом** портале. Юнит-тесты (`pnpm test`)
проверяют правила на подставных данных. Смок проверяет, что портал отвечает так, как ждёт код:
- те же запросы (`app/utils/invoiceRequests.ts`);
- то же листание (`app/utils/paging.ts`);
- тот же разбор и расчёт (`shared/domain/*`);
- тот же клиент BitrixGPT (`server/utils/llm.ts`), что у приложения.

Смок **пишет в портал**: создаёт сделку, счета, задачи, записи времени, позиции счёта и дело.
Поэтому он отдельный от `pnpm test`, в CI не запускается, а пишет только на порталы из списка
тестовых.

Подход — по образцу живых проверок ai-price-import (`scripts/lib/envFile.mjs`,
`testPortalGuard.mjs`), вместе с их граблями (см. «Окружение»).

## Когда запускать

- Поменялся запрос к порталу: `app/utils/invoiceRequests.ts`, `useInvoiceFill.ts`, `useCatalog.ts`.
- Поменялся разбор ответа: `shared/domain/tasks.ts`, `invoice.ts`, `currency.ts`, `app/utils/measures.ts`.
- Поменялся расчёт (`shared/domain/fill.ts`, `markup.ts`, `time.ts`) или промпты BitrixGPT.
- Обновился b24jssdk.
- Время от времени: портал меняется без нас.

## Окружение

Git-ignored файл `.env.b24test` в корне (шаблон — `.env.b24test.example`), или другой путь в
`SMOKE_ENV_FILE`:

```bash
B24_HOOK=https://<тестовый-портал>.bitrix24.by/rest/<id>/<код>/   # входящий вебхук администратора
VIBE_API_KEY=vibe_api_…                                            # необязательно: без него BitrixGPT пропускается
```

- **Адрес портала берётся только из файла**, переменная окружения `B24_HOOK` не читается. В
  оболочке может жить `B24_HOOK` другого, боевого портала: в ai-price-import так уже уходили не
  туда.
- **Ключ BitrixGPT — тоже только из файла** (`BITRIXGPT_API_KEY`, затем `VIBE_API_KEY` — порядок
  как у сервера): ключ другого проекта из окружения тратил бы чужую квоту.
- Из файла берётся последнее вхождение ключа, кавычки снимаются, `export KEY=` понимается.
  Закомментированный `#KEY=` и ключ-суффикс (`OLD_B24_HOOK`) не подхватываются.
- **Страж.** Писать можно только на портал из `smoke/lib/env.ts → TEST_PORTALS`. Другой домен —
  только с явным согласием, где домен назван руками: `B24_SMOKE_YES_TARGET=<домен> pnpm smoke`.
- Секрет вебхука в вывод не попадает: ошибки несут метод и текст портала, адреса вырезаются
  (`smoke/lib/portal.ts`).

Нет файла или в нём нет `B24_HOOK` — все проверки пропускаются, в портал ничего не пишется.

```bash
pnpm smoke                                     # .env.b24test из корня
SMOKE_ENV_FILE=/path/.env.b24test pnpm smoke   # файл в другом месте
pnpm smoke smoke/ai.smoke.ts                   # один набор
```

Полный прогон — около полутора минут. BitrixGPT тратит 6 обращений к модели за прогон.

## Что делает прогон

**Засев** (`smoke/setup.ts`, `smoke/lib/seed.ts`). У каждого прогона свои данные с меткой
`IFT smoke <дата время>`, поэтому прогоны друг другу не мешают. Прогон создаёт:
- сделку в базовой валюте портала;
- счета:
  - в другой валюте (USD) из сделки;
  - в базовой валюте из сделки;
  - без сделки;
  - для листания позиций (55 строк) — у него «Реквизиты вашей компании» сняты;
- «Реквизиты вашей компании» `IFT smoke: реквизиты вашей компании` — **одни на все прогоны**
  (ищутся по названию, нет — создаются): список реквизитов видят люди, засорять его не нужно.
  Счета из сделки и без сделки привязаны к ним; новый счёт портал и так получает «моей компанией»
  по умолчанию, поэтому у счёта листания реквизиты снимаются `crm.item.update`;
- задачи с тегами и привязками:
  - «дизайн» — `D_`, теги «Дизайн» и «Срочно», запись сегодня и запись задним числом, до смены ставки;
  - «сервер» — `D_`, без тегов, записи 90 и 10 минут;
  - «звонок» — `D_`, одна запись 15 минут: в типе 1 к ближайшему часу она обнуляется;
  - «консультация» — `SI_`, тег «ЧЧ1»;
  - «доработка» — `T1f_`, запись без описания;
  - чужая задача;
  - задача с 55 записями времени;
- результат задачи.

**Данные не удаляются**: решение владельца, их оставляют для ручного просмотра. Найти их в
портале можно по метке прогона.

| Набор | Что проверяет |
|---|---|
| `rest.smoke.ts` | формы ответов: `profile.ADMIN` — логическое; курсы; подписи единиц измерения; фильтр задач объектом (массивом — 400); непонятный фильтр отдаёт всё; код привязки без учёта регистра; теги в списке задач; листание записей времени (55 → 2 запроса, `total` нет) и позиций (55 → 2 страницы); дата записи задним числом; `tasks.task.result.list` v3; `user.get` пакетом; `app.option` вебхуку недоступен; ставки НДС портала (`catalog.vat.list`); «моих компаний» список — реквизиты засева есть, обычные компании нет |
| `invoice.smoke.ts` | **72 варианта расчёта**: источник (сделка → счёт в другой валюте / в валюте ставок; задачи счёта) × тип 1/2 × округление (нет / 30 мин вверх / 60 мин к ближайшему) × наценка (нет / по тегам) × как строка ложится в счёт (цена часа × часы / сумма × 1). Каждая строка сверяется с независимой формулой: время, округление, ставка на дату, наценка по первому совпадению, курс, цена часа, сумма, цена и количество по режиму, ставка НДС счёта (20%). Сверяются число строк, ошибки (запись без описания) и предупреждения (курс, смена ставки, ноль после округления). Отдельно: счёт без сделки при источнике «сделка», счёт без реквизитов (`mycompanyId = 0` → остановка), валюта без курса, нет ставки. Запись с НДС 20%: «Заменить» (позиции совпали с предпросмотром; `price` — с налогом, `priceExclusive` — цена предпросмотра, `taxIncluded = N`; сумма и налог счёта — ровно итоги предпросмотра), «Добавить» в режиме «сумма × 1» (сортировка после существующих, количество 1, итог всего счёта сошёлся), пакет с ошибкой посередине («добавлено 1 из 3»). Дело консультации: вебхук его создать не может (`ERROR_WRONG_CONTEXT` — метод только для приложения, вид записи закрепляют юнит-тесты), иконка `ai-process` и логотип `ai-copilot` есть в портале |
| `ai.smoke.ts` | BitrixGPT: названия типа 2 и типа 1, полный пакет из 25 строк, «инструкция» в тексте задачи не ломает формат, консультация текстом, неверный ключ даёт понятный отказ `auth` |

## Как читать красное

- **Красный вариант в `invoice.smoke.ts`** — расчёт на живых данных разошёлся с формулой. Имя
  варианта называет сочетание настроек, а сообщение — поле строки. Сначала проверьте, не
  поменялась ли форма ответа портала (`rest.smoke.ts` рядом покажет).
- **Красный `rest.smoke.ts`** — портал отвечает иначе, чем записано в `docs/REST_METHODS.md`.
  Замерьте, поправьте код и строку реестра.
- **Красный `ai.smoke.ts`** — модель сменила поведение, ключ истёк или кончилась квота. Текст отказа
  разбирает `describeLlmFailure`.

## Замеченное на живом портале

Для истории, подробно — `docs/REST_METHODS.md`:
- **Тег — одна запись на весь портал.** Если тег «дизайн» уже есть, задача с тегом «Дизайн»
  получит «дизайн». Поэтому теги сравниваются без учёта регистра (`shared/domain/markup.ts`).
- У системных единиц измерения `measureTitle` и `symbol` — `null`. Подпись берётся из ОКЕИ.
- `task.elapseditem.getlist` не отдаёт `total`. За последней страницей — пусто.
- Пакет v3 с одной ошибочной командой отказывает целиком, без ответов команд (замер 2026-09-24;
  смок пакет v3 не гоняет — приложение его не использует).

## Как добавить проверку

- Новый запрос к порталу — сначала в `app/utils/invoiceRequests.ts` (им пользуется и страница),
  потом проверка формы в `rest.smoke.ts`.
- Новое правило расчёта — строка в таблице ожиданий `invoice.smoke.ts`. Ожидание пишется
  **независимо**, а не вызовом той же функции: иначе проверка повторит ошибку кода.
- Новые данные — в `smoke/lib/seed.ts`, с меткой прогона в названии.
