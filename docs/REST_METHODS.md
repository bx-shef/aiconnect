# Исходящие вызовы REST Битрикс24

> Last reviewed: 2026-09-26

Реестр каждого метода, который зовёт приложение. Добавили вызов в код — добавьте строку сюда:
`tests/repoGuards.test.ts` сверяет строковые имена методов в `app/`, `server/`, `shared/` с этим
файлом и краснеет на пропуске. Из этого же списка собирается набор прав приложения.

Сигнатуры здесь не дублируются: их источник — MCP `b24-dev-mcp` (`bitrix-search` →
`bitrix-method-details`). Здесь — то, чего в документации нет: кто зовёт, каким транспортом, чьими
правами и на какие грабли уже наступили.

**Транспорт.** «Фрейм» — `@bitrix24/b24jssdk` во фрейме портала (`app/composables/useB24.ts`),
правами сотрудника, открывшего страницу. «Сервер: фрейм-токен» — наш Nitro зовёт портал токеном
того же сотрудника (`server/utils/b24Client.ts → makeFrameCall`). «Сервер: установщик» — токеном
администратора, установившего приложение (`makePortalCall`), только там, где прав сотрудника не
хватает по документации.

**Статус.** 📄 — сверено с документацией MCP, на живом портале НЕ проверялось; ✅ — проверено
на тестовом портале (2026-09-24) **вебхуком администратора** тем же b24jssdk и теми же
параметрами, что в коде: форма запроса и ответа, сквозной сценарий счёта на чистых функциях
приложения. Из фрейма и правами обычного сотрудника это ещё не прогонялось, а методы, которым
нужен контекст приложения (`app.option.*`, `placement.*`, `event.*` — вебхуку «Application context
required»; `app.info` отвечает без `CODE`), остаются 📄 до установки на портал
([#2](https://github.com/bx-shef/invoice-from-tasks/issues/2)).

**Версия REST.** Правило владельца: работаем через b24jssdk и **берём REST v3, где метод в нём
есть**. По документации (статья «Обзор REST 3.0», сверка 2026-09-24) v3 сейчас покрывает только
задачи (и модули, которых мы не зовём: база знаний, почта, структура компании, журнал событий,
учёт рабочего времени). Поэтому:

- **v3** (`b24.callV3` → `actions.v3.call`, адрес `/rest/api/…`): `tasks.task.result.list`.
  Фильтр — массив троек `[поле, оператор, значение]`, связанные объекты — через точку в `select`,
  логические значения — `true/false`, не `Y/N`.
- **v2** — всё остальное: CRM, каталог, сотрудники, настройки, встройки, события — в v3 их нет;
  `tasks.task.list` — фильтр v3 понимает только `id`, а нам нужен поиск по привязке к CRM
  (замер: `crmItemIds` — «требуется атрибут Filterable»); `task.elapseditem.getlist` — метода v3
  нет, `elapsedTime` в v3 `tasks.task.get` не возвращается (замер).
- **Исключение владельца — теги задач из v2** (2026-09-24): v3 отдаёт теги только в
  `tasks.task.get` — отдельный запрос на задачу (пакетами по 50), а пакет v3 при одной ошибке
  отказывает целиком. v2 `tasks.task.list` с `select: ['TAGS']` отдаёт их в том же списке, что
  мы и так читаем, — ноль лишних запросов. Вернуться к v3 — issue
  [#13](https://github.com/bx-shef/invoice-from-tasks/issues/13).
- Пакет v3 — отдельный запрос: смешивать в нём методы v2 нельзя (у версий разные адреса), и
  портал выполняет его целиком или никак (замер).
- Ограничения v3 выше — замер 2026-09-24. Смок их не проверяет: владелец решил перепроверять
  руками время от времени (issue #13). Появится нужное в v3 — переводим и отмечаем здесь. Формы
  ответов методов, которые вызывает приложение, держит смок (`pnpm smoke`, `docs/SMOKE.md`).

Метод REST v3: условие по `taskId` в `filter` обязательно, `pagination.limit`, ответ — `text` у каждого результата. Шлём тройку `['taskId', '=', id]` (форма фильтра из «Обзора REST 3.0», её знают типы SDK); пример страницы метода — пара `['taskId', 51]`. Какую форму примет портал — проверить на смоке #2. Сбой не останавливает заполнение. Замер: принимает и тройку, и пару; ответ — `{ items: [{ id, text }] }`; без фильтра — ошибка валидации. Через `/rest/` (v2) метод тоже отвечает — массивом. | ✅ |

⚠ **Право называется `task`**, хотя страницы `tasks.task.*` пишут `tasks`: документация
противоречит сама себе, живой портал принял `task` (замер get-task-from-b24, 2026-08-26).

**Код привязки задачи к счёту.** Для сделки — `D_<id>` (документация). Для нового счёта —
`SI_<id>`: так его называет v3 (`crmItemIds`: «`SI_XX` — счёт»), а в настройках поля
`UF_CRM_TASK` на тестовом портале тип значится `SMART_INVOICE` (замер 2026-09-24). Портал хранит
код как записали: задачи с `SI_2` и с `T1f_2` (31 = 0x1f) обе находятся своим фильтром, — поэтому
ищем по обоим (`crmBindingCodes`). Какой код ставит сам интерфейс, привязывая задачу из карточки
счёта, — посмотреть глазами на #2.

## Не REST, но рядом

- `$b24.installFinish()`, `$b24.parent.setTitle()`, `$b24.dialog.selectUser(s)()`,
  `$b24.placement.options` — методы фрейма b24jssdk (документация: `https://bitrix24.github.io/b24jssdk/llms.txt`).
- `https://<сервер авторизации>/oauth/token/` — продление токена: при установке — для сверки
  `member_id` и домена (`server/utils/verifyInstallMember.ts`), для токена установщика — внутри
  b24jssdk (`server/utils/b24Client.ts`). Сервер — из `auth[server_endpoint]` события установки
  (документация события: «Адрес сервера авторизации для обновления токена»), только из белого
  списка `oauth.bitrix24.tech` / `oauth.bitrix.info` (`b24Host.ts → resolveOAuthHost`), и
  хранится в записи о портале. Без поля — `oauth.bitrix24.tech` (текущая документация: «Автоматическое
  продление токенов OAuth 2.0», «Коды ошибок сервера авторизации»). 📄
- В ответе продления `client_endpoint` — REST-адрес **портала**, а `domain` — хост **сервера
  авторизации**. Домен установки сверяем по `client_endpoint`.
- `keepAuthFresh` из документации b24jssdk в установленной 2.2.0 нет — токен фрейма перед
  запросом к нашему серверу обновляем сами (`app/utils/frameToken.ts`, `docs/ARCHITECTURE.md`).
- b24jssdk по умолчанию **повторяет** запрос при сетевой ошибке, таймауте и ответе 5xx
  (`retryOnNetworkError`, до 3 попыток — код пакета 2.2.0). Приложение пишет то, что повторять
  нельзя (`crm.item.productrow.add`, `crm.activity.configurable.add`, `placement.bind`), поэтому повторы
  выключены один раз при создании фрейма (`app/config/b24.ts → sdkRestrictionParams`,
  `initializeB24Frame({ restrictionParams })`). Невыполненные порталом запросы (лимиты, 429) SDK
  по-прежнему повторяет. Чтение при сетевом сбое само не повторяется — сотрудник повторит кнопкой.
- `https://vibecode.bitrix24.tech/v1` — BitrixGPT (OpenAI-совместимый AI Router Вайбкода), `server/utils/llm.ts`.
