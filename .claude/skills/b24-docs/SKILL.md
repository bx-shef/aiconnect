# Документация Битрикс24: где смотреть и на что не наступать

> Last reviewed: 2026-09-26

Правило — `docs/AGENT_RULES.md` §1: API не вспоминают, его читают.

## Где смотреть

| Что | Как |
|---|---|
| REST: метод, параметры, ответ, ошибки | MCP `b24-dev-mcp`: `bitrix-search` (запрос по-русски или по-английски) → `bitrix-method-details` с точным именем; `field: params` / `returns` / `errors` / `examples`, чтобы не тянуть всё |
| События | `bitrix-search` с `doc_type: ["event"]` → `bitrix-event-details` |
| Встройки, права, установка | `bitrix-search` с `doc_type: ["other", "app_development_docs"]` → `bitrix-article-details` / `bitrix-app-development-doc-details` (например «Каталог точек встраивания», «Мастер установки локального приложения») |
| `@bitrix24/b24jssdk` | `https://bitrix24.github.io/b24jssdk/llms.txt` → нужная страница `…/raw/docs/….md` |
| `@bitrix24/b24ui` | `https://bitrix24.github.io/b24ui/llms.txt` → страница компонента |
| Что реально в установленной версии SDK | типы пакета: `node_modules/@bitrix24/b24jssdk/dist/esm/index.d.ts` |
| Что уже проверено и какие грабли | `docs/REST_METHODS.md` |

## Известные расхождения — проверять в первую очередь

- **MCP смешивает REST v2 и v3.** Страницы `tasks.task.list`, `tasks.task.get`,
  `tasks.task.result.list` описывают форму v3 (фильтр массивом). Правило владельца — брать v3,
  где метод в нём есть, и звать его явно через `b24.callV3` (`actions.v3.*`, `/rest/api/…`);
  исключения владельца (теги задач из v2-списка, #13) записаны в таблице «Версия REST». Метод,
  который зовём через v2 (`b24.call`, `/rest/`), получает v2-форму:
  фильтр **объектом**, форма v3 отвергается с 400 (замер get-task-from-b24). Какой метод на какой
  версии — таблица «Версия REST» в `docs/REST_METHODS.md`.
- **Тег задачи — одна запись на весь портал**: «Дизайн» в новой задаче станет уже существующим
  «дизайн» (замер 2026-09-24). Теги сравнивать без учёта регистра.
- **Живой портал проверяет `pnpm smoke`** (`docs/SMOKE.md`): формы ответов, 72 варианта расчёта,
  запись в счёт, BitrixGPT. Поменял запрос или разбор — прогони.
- **`bitrix-article-details` подбирает статью по похожему названию**, а не по точному: на
  «Обзор REST 3.0» он вернул «Поля задачи в REST 3.0». Сверяйте заголовок ответа.
- **Непонятый фильтр не отвергается, а игнорируется** — `tasks.task.list` отдаёт все задачи.
  Результат фильтра всегда перепроверять своим кодом.
- **Право задач — `task`**, хотя страницы `tasks.task.*` пишут `tasks`.
- **Числа приходят строками**, регистр ключей зависит от метода (`tasks.task.list` — camelCase,
  `task.elapseditem.getlist` — UPPER_CASE).
- **`task.elapseditem.getlist`** — позиционные параметры массивом, страница до 50; `total` в
  ответе нет (замер 2026-09-24).
- **`catalog.measure.list`** — у системных единиц `measureTitle` и `symbol` приходят `null`
  (замер 2026-09-24): название — из ОКЕИ по коду (`app/utils/measures.ts`).
- **Пакет v3 — целиком или никак**: одна упавшая команда — весь пакет неуспешен без ответов
  команд (замер 2026-09-24). Кто именно упал, узнаётся только одиночными вызовами.
- **`app.option.set`** — только администратор; размер хранилища REST-документация не называет
  (`docs/SETTINGS.md`, «Сколько влезет»).
- **`crm.item.productrow.set`** заменяет все позиции; у позиции без цены цена станет 0.
- **`price` строки — цена С налогом**, `priceExclusive` только для чтения: НДС сверху — это
  `price = цена × (1 + ставка)`, `taxRate`, `taxIncluded: 'N'` (замер 2026-09-26). Итог счёта —
  одно округление, налог — по строкам (`vatTotals`).
- **Новый счёт сам получает «моей компанией» по умолчанию** (`mycompanyId`), даже с `0` в
  `crm.item.add`; снять — только `crm.item.update`.
- **Встройка нового счёта**: ID приходит в `PLACEMENT_OPTIONS.ENTITY_ID`, не в `ID`.
- **b24jssdk**: документация опережает релиз — `keepAuthFresh` описан, но в 2.2.0 его нет.
  `getAuthData().domain` — с протоколом; `expires` — секунды эпохи.
- **Сервер авторизации у портала свой** — `auth[server_endpoint]` события установки. Текущая
  документация называет `oauth.bitrix24.tech`, эталоны ходили на `oauth.bitrix.info`; берём из
  события по белому списку облачных серверов (`server/utils/b24Host.ts`). Коробку сервером
  авторизации не принимать: она может «подтвердить» любой `member_id`. В ответе продления токена
  `client_endpoint` — REST-адрес **портала**, а `domain` — хост **сервера авторизации**: портал
  определять по `client_endpoint`.
- **b24jssdk сам повторяет запросы** при сетевой ошибке, таймауте и 5xx (`retryOnNetworkError`,
  до 3 попыток). Для записи, которую нельзя повторять (`*.add`), это дубли: в приложении повторы
  выключены при создании фрейма (`app/config/b24.ts → sdkRestrictionParams`), а результат записи
  сверяется перечитыванием. Переключать настройки SDK на каждую запись нельзя — ограничитель
  запоминает текущие значения как исходные.
- **Пакет с ошибкой команды** SDK помечает неуспешным целиком, но ответы команд оставляет в
  данных (`returnAjaxResult`) — упавшую команду можно назвать.
- **`crm.activity.todo.add` даёт в ленте две записи** — открытое дело и серого двойника в истории
  (пробы 2026-09-26). Запись «для чтения» — конфигурируемое дело, закрытое сразу
  (`crm.activity.configurable.add`): оно **только из контекста приложения**, вебхук получает
  `ERROR_WRONG_CONTEXT`. Внешний текст в BB обезвреживаем до своих тегов.

## Как записать результат

- Новый метод в коде — строка в `docs/REST_METHODS.md` (иначе краснеет `tests/repoGuards.test.ts`).
- Документация и портал разошлись — записать в `docs/REST_METHODS.md`, что замерено, как и когда;
  статус 📄 → ✅ только после живой проверки.
- В описании PR — какие страницы документации прочитаны.
- Документация молчит — так и написать: «не нашёл в документации», и что сделано взамен.
