# Ревью PR: /code-review + панель из пяти

> Last reviewed: 2026-09-28

Источник правил — `docs/AGENT_RULES.md` §3. Этот навык — порядок действий.

## 1. Подготовка

1. `git fetch origin main && git merge origin/main` в ветку PR (не rebase чужой ветки). Конфликты —
   решить и прогнать `pnpm check`.
2. Написать **простым языком**, о чём PR: что делает и зачем, в 3–6 строк. Не выходит коротко —
   PR делает слишком много, сказать об этом.

## 2. Запуск — одновременно

- `/code-review` по диффу PR (с разных сторон).
- Панель нужна, если сработал триггер из `docs/AGENT_RULES.md` §3.1 п. 4 (сомневаешься — собирай).
  Тогда пять сабагентов одним сообщением (параллельно): `reviewer-docs`, `reviewer-dev`,
  `reviewer-qa`, `reviewer-security`, `reviewer-cto` (`.claude/agents/`, модель Sonnet). Каждому —
  номер PR и общие условия ниже (они же зашиты в определения агентов):

| Роль | Задача |
|---|---|
| Документация и Skill | `docs/`, `README.md`, `CLAUDE.md`, `.claude/skills/` — точность против кода, полнота, работают ли примеры и ссылки |
| Программист | адекватность решений, JSDoc, типизация TS, дублирование, прочее на усмотрение |
| Тестировщик | покрытие тестами и качество тестов; правки страниц — отрисовываются ли они, а не только логика (`AGENT_RULES.md` §5.3а); мутации — только в отдельном `git worktree` |
| Безопасность | подлинность запросов к `completions_url`, SSRF через `callbackUrl`, хранение ключей клиентов, секреты в журналах, фрейм-авторизация, лимиты |
| Технический директор | изменение целиком: объём, цена, направление, обязательства проекта |

Общие условия — вписать в промпт каждому дословно по смыслу:

- Проект большой: ограничь чтение, начни с диффа (`git diff origin/main...HEAD --stat`), не грузи
  всё дерево, не упади по таймауту.
- Рабочее дерево общее: чужая правка — сосед, не откатывать.
- Код меняет только тестировщик и только в отдельном `git worktree`; откат — из копии, никогда
  `git checkout --`.
- Ревьюеры сообщают находки (файл:строка, что, почему, как исправить, насколько уверен) — не чинят.
- API Битрикс24, b24jssdk, b24ui — сверять с документацией (навык `b24-docs`), не по памяти.

## 3. Отчёт владельцу — по-русски, коротко

Блок на ревьюера: **кто — что — почему важно — как исправить**. Без простыней и пересказа
транскриптов. Отдельной строкой — находки, которые берёшь, и которые нет (с причиной и замером).

## 4. Исправления

- Всё правится **в этом PR**. Кажется, что находка просится в отдельный issue/PR — не выносить
  молча, а спросить владельца.
- Каждое исправление гарда — с тестом, который краснеет при мутации (`AGENT_RULES.md` §5.2).
- После исправлений: `pnpm check`, `pnpm build`, пуш. Доработка существенная — панель заново.
